Section 01

Organizational Context, Problem & My Role

At the Royal Thai Survey Department (RTSD), field survey teams continuously record and verify Ground Control Points (GCPs) under the L7018 military map series standard (UTM Zone 47N) across the Bangkok Metropolitan Area.

Under the supervision of the Data Service & Map Information Center, I served as a Spatial Data Engineering Intern responsible for end-to-end backend architecture redesign, empirical load benchmarking, spatial query optimization, and interactive GIS dashboard development using synthetic mock datasets (up to 1,000 GCPs) to protect classified military survey records.

Per-Request Connection Overhead

The legacy architecture opened and closed a fresh psycopg2 database connection on every HTTP request, causing severe CPU/RAM overhead under concurrent field requests.

Pool Exhaustion & Sequential Scans

Under 25–50 concurrent users, un-tuned pooling (maxconn=20) saturated available connections (60% failure at 50 users), while unindexed spatial queries triggered full-table sequential scans.

Technical Clarification on Concurrency vs. Calculation Accuracy: High concurrency impacts latency, throughput, and connection availability (HTTP 500 / Timeout) due to resource contention—it does not alter floating-point coordinate calculation accuracy (which depends strictly on pyproj algorithms and PostgreSQL double precision data types).

Section 02

Engineering Solution & Implementation

To eliminate connection bottlenecks, enforce geometric data quality, and accelerate spatial filtering, I implemented four core architectural components (all code snippets below are sanitized and verified safe for public release):

1

Threaded Connection Pool with FastAPI Lifespan (maxconn=65)

Eliminating per-request TCP handshakes with thread-safe connection reuse and guaranteed cleanup.

After benchmarking SimpleConnectionPool (maxconn=20) and identifying saturation at 25–50 users, I upgraded to ThreadedConnectionPool(minconn=5, maxconn=65) bound to FastAPI's @asynccontextmanager lifespan. The ceiling of 65 connections was specifically calibrated for our 50–60 concurrent user prototype test scope (50 active worker connections + 15 reserve connections for real-time health monitoring), wrapped in try...finally blocks to prevent connection leaks. 

from contextlib import asynccontextmanager
from fastapi import FastAPI
from psycopg2.pool import ThreadedConnectionPool

db_pool = None

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Initialize thread-safe pool scoped for 50-60 concurrent users + monitoring reserve
    global db_pool
    db_pool = ThreadedConnectionPool(minconn=5, maxconn=65, dsn=DATABASE_URL)
    yield
    if db_pool:
        db_pool.closeall()

app = FastAPI(lifespan=lifespan)
2

Geometric Boundary Validation (ST_Contains) & Proximity Search (ST_DWithin)

Upgrading from coarse bounding boxes to true polygon geometry validation and radius queries.

Incoming WGS84 coordinates pass through API Key authentication and Pydantic validation before PostGIS verifies point-in-polygon containment against Bangkok administrative boundaries using ST_Contains (rejecting out-of-bounds points with HTTP 422). Additional endpoints support batch UPSERT (execute_values), radius search (ST_DWithin), and RFC 7946 GeoJSON export. 

-- Verify point lies inside true Bangkok polygon boundary & query nearby GCPs
SELECT id, point_name, utm_easting, utm_northing,
       ST_Distance(geog, ST_SetSRID(ST_MakePoint(%s, %s), 4326)::geography) AS distance_m
FROM survey_points
WHERE ST_DWithin(geog, ST_SetSRID(ST_MakePoint(%s, %s), 4326)::geography, %s)
ORDER BY distance_m ASC;
3

Coordinate Engine (pyproj)

Transforms WGS84 geographic coordinates (EPSG:4326) into UTM Zone 47N (EPSG:32647) with double-precision storage in PostgreSQL, ensuring consistent, survey-grade coordinate accuracy independent of request concurrency.

4

GiST Spatial Indexing & Query Tuning

Analyzed query plans via EXPLAIN (ANALYZE, BUFFERS) and created R-Tree GiST indexes (USING GIST) alongside periodic VACUUM ANALYZE, shifting execution plans from full-table Sequential Scans to sub-millisecond Bitmap Index Scans.

Section 05 • Advisor Feedback & Technical Resolution

Addressing Evaluation Questions & Consistency

Following the evaluation session, key questions and consistency notes were audited and resolved across the report, slides, and portfolio so that root causes, experimental baselines, and conclusions align consistently.

1. Tuning Conclusion & Fair Baseline • เกณฑ์การสรุปผลการจูน

Tuning validity is established by comparing identical concurrency levels—specifically 50 Concurrent Users before tuning (40.0% success, 19.95 req/s) vs. 50 Concurrent Users after tuning (100.0% success, 32.40 req/s)—rather than comparing 25 pre-tuning users directly against 50 post-tuning users.

การสรุปผลการจูนอิงจากการเปรียบเทียบที่ภาระงานเดียวกัน (50 Users ก่อนจูนสำเร็จ 40.0% เทียบกับหลังจูนสำเร็จ 100.0%) ส่วนระดับ 25 Users เป็นจุดเริ่มสังเกตอาการคอขวดและ 60 Users เป็นการทดสอบขั้นสูงหลังเพิ่มดัชนี GiST

2. Concurrency vs. Decimal Accuracy • ผลของจำนวน User ต่อความแม่นยำทศนิยม

Higher concurrent user count affects connection pool availability, queueing, latency, and timeout/HTTP 500 error rates—it does not cause floating-point calculation errors, which depend on numerical algorithms, rounding logic, and database data types (double precision / numeric).

จำนวนผู้ใช้งานพร้อมกันส่งผลต่อ Latency การแย่งทรัพยากร และโอกาสเกิด Timeout/HTTP 500 แต่ไม่ได้ทำให้การคำนวณจุดทศนิยมผิดพลาดตามจำนวนคน ซึ่งขึ้นกับอัลกอริทึมและการกำหนดชนิดข้อมูลเป็นหลัก

3. Why maxconn=65 & Scaling Beyond • เหตุผลของท่อ 65 และการขยายสู่ 1,000 Users

maxconn=65 was intentionally scoped for prototype load testing up to 50–60 concurrent users (plus monitoring headroom). Scaling to 1,000+ concurrent users is scoped as future architecture work using an external PgBouncer pooler, load balancing, and caching rather than opening 1,000 direct in-app pool connections.

ค่า maxconn=65 กำหนดไว้สำหรับขอบเขตการทดสอบต้นแบบ 50–60 ผู้ใช้งานพร้อมกัน ส่วนการรองรับระดับ 1,000+ ผู้ใช้งานอยู่ในแผนต่อยอดด้วย PgBouncer, Load Balancer และ Caching ไม่ใช่การขยาย Pool ในแอปตรงๆ เป็น 1,000 ท่อ

4. Logic Alignment & Query Speed-Up • ความสอดคล้องของเนื้อหาและความเร็ว Query

Workload figures, problem root causes, and conclusions are synchronized across sections, while query speed-up is supported by shifting from full-table Sequential Scans to GiST Bitmap Index Scans and tracking P50/P95 latency alongside the three verification pillars (Concurrent Logging, Real-Time Analysis, Verify Evidence).

ปรับตัวเลขภาระงาน เหตุผลคอขวด และข้อสรุปให้สอดคล้องกันทั้งเล่มและหน้าเว็บ พร้อมอธิบายการเพิ่มความเร็วของ Query จากการเปลี่ยนจาก Sequential Scan เป็น GiST Index Scan ควบคู่กับกรอบตรวจสอบผลลัพธ์ทั้ง 3 ส่วน

Section 06

Lessons Learned, Reflection & Future Scalability

Key Lessons Learned

  • Fair Benchmarking Discipline: Comparing identical workloads (50 users before vs. 50 users after) is essential to prove optimization impact scientifically.
  • Concurrency vs. Accuracy: Resource contention causes timeouts and HTTP 500s—not numerical drift—while GiST R-Tree indexes prevent full-table scans under load.
  • Security-First Engineering: Learned how to design, benchmark, and document mission-critical GIS infrastructure safely using synthetic mock data under defense compliance rules.

What I Would Do Differently

  • Automated Benchmarks From Day 1: Set up automated Locust regression scripts during Week 1 so every architectural change is measured against identical workloads immediately.
  • Containerized Stack Early: Package FastAPI and PostGIS in Docker Compose from the start to standardize resource limits and simplify deployment handoff.
  • Earlier Field User UI/UX Testing: Share interactive Streamlit prototypes earlier with RTSD survey staff to refine map marker clustering and buffer filters sooner.

Scaling to 1,000+ Users

  • PgBouncer Multiplexing: Introduce PgBouncer in transaction pooling mode rather than scaling in-app ThreadedConnectionPool directly to 1,000 sockets.
  • Nginx & Multi-Worker Replicas: Scale FastAPI horizontally across multiple Uvicorn workers behind an Nginx load balancer.
  • Redis Spatial Caching: Cache repeated polygon boundary checks and proximity queries in Redis to achieve sub-10ms latency at enterprise scale.
